# OD-004 · plugin-free Figma import: manual validation · 2026-07-12 · OPEN
| Field | Value |
|---|---|
| Decision | An OPEN spike, not a ruling: whether the aliased DTCG export's `com.figma.aliasData` (`targetVariableName` + `targetVariableSetName`) resolves the live raw→semantic cascade on native Figma import without the plugin is unverified and must be checked by hand. The document fixes the procedure: import `figma-aliased/palette.tokens.json` (expect a `Color Primitives` collection), then `Light_tokens.json` and `Dark_tokens.json` (expect a `Color Roles` collection, #491, with Light + Dark modes and 53 semantic variables per palette), then inspect a semantic variable; PASS if its values show as alias chips and editing a primitive cascades, FAIL if values import as resolved colors or Figma reports import errors. |
| Forces | There is no Figma in CI, Figma's docs say name+collection `aliasData` resolves on native import only when the target collection already exists (ADR-002, re-verified 2026-06-15), the resolved `figma/` export (no `aliasData`, no cascade) and the plugin remain the reliable paths |
| Rejected | none named |
| Consequences | On PASS, OD-004 can move toward DECIDED and `figma-aliased/` may be promoted from "experimental" to a documented plugin-free path. On FAIL, the plugin stays the cascade path, OD-004 stays OPEN, and the README's "unverified" framing stands. The result (Figma version, date, PASS/FAIL, screenshots) is to be recorded in `docs/spec/CHANGELOG.md` and ADR-002 / OD-004 updated accordingly. Issue named: #491 (collection rename to `Color Roles`). |
