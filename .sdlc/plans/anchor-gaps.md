# Anchors a palette did not get: pre-v5 kits and hueless samples (#740, #744)

Two gaps left by #681's stored anchors, both about what a palette carries when it was never sampled through the new path.

The first (#740) is persistence. A kit saved before schema v5 (persist.js `CURRENT_SCHEMA_VERSION` was `4` at 7d20c42d, the commit before #681 landed) has no `anchor` on any palette, and `hydrate()` keeps absence absent by design, so the kit renders through the non-anchored path with no notice. The critic on PR #737 measured it on the one document every user has: a saved, unedited default kit renders `16/16` ramps differently from a fresh default. Measured again here at 7d325b32 by stripping `anchor`/`sourceAnchor` and `schemaVersion` from a serialized `defaultDocument()`: `16 of 16` ramps differ. The fix is a provenance backfill in `hydrateStoredDoc` (the seam that already stamps `hueSpace: "cam16"` on a pre-`hueSpace` stored doc): a palette in a pre-v5 stored doc that still equals a default-kit row on name, hue, chroma, skew and lift regains that row's `anchor` and `sourceAnchor`. Measured with that rule at 7d325b32: `0 of 16` ramps differ, `16` anchors stamped, a row whose hue was edited by one degree is left alone (`15` stamped), and a v6 doc without anchors is untouched (`0`). Everything else in a pre-v5 doc stays parametric, on purpose and documented: a user-built palette has no source colour to anchor to (the New-Palette modal stores none even today), and a stored curated preset cannot be matched to today's corpus because #681's regeneration changed `lift` on `3363` of `3780` palettes (only `417` rows and `5` presets are equal on all four numbers), so a backfill there would pin today's anchor onto yesterday's fitted shape. Q1 puts the wider options to the owner.

The second (#744) is the generator. `scripts/gen-categories.mjs`'s `palette()` stores `Math.round(oklch[2])` as a sample's hue, and a hueless sample (`"oklch": "1.000 0 0"`, the only one in the corpus: Nike "Box white", `#FFFFFF`) stores hue `0`. Since #739 an achromatic anchor renders its ramp at the palette's stored hue, so that palette renders a mauve ramp at hue 0 (`650:#B8969F`, max CAM16 C `33.21`). The fix is one rule in the generator: a hueless sample takes the entry's derived neutral hue, `Math.round(deriveNeutral(swatches)[2])`, the same chroma-weighted circular mean `deriveNeutralPalette` already uses for the entry's neutral, `36` for Nike. Measured at 7d325b32 with the generated file patched to hue 36: `650:#B8988F`, max CAM16 C `27.28`, stop 650 CAM16 hue `35`, the four sampled colour gates green, and the full tonal gate red on exactly the re-freeze the design names (revision 6: four new `KNOWN_BASELINE_DUP` keys at hue 36, the five hue-0 keys gone; the planner's run printed only the `peak` line because the gate keeps one message per gate name, see the 2026-09-29 Measured table).

## The design, stated once

U1 (#740). In `src/ui/model.mjs` the `DEFAULT_PALETTES` declaration gains `export` (one word, no other change; `defaultDocument()` stays the app's source). In `src/ui/app-helpers.mjs` a pure exported function `backfillDefaultAnchors(stored)` returns the same object when `stored.schemaVersion` is a finite number at or above `5`; otherwise a copy in which every palette that has no `anchor` and equals, on `name`, `hue`, `chroma`, `skew` and `lift`, a row of the one default table the stored doc's hue space selects gets that row's `anchor` as both `anchor` and `sourceAnchor`. The table is chosen once per call from `stored.hueSpace`, read as the seam reads it: `"cam16"`, or the field absent or `null` (`stored.hueSpace == null`), selects the raw `DEFAULT_PALETTES` rows (the CAM16-hue form: a doc saved before the field existed, 2026-06-28, or a doc stored under `cam16` since); any other value selects `defaultDocument().palettes` (the OKLCH-hue form), which is also what `hydrate`'s enum clamp turns an unknown value into, so the table always matches the space the doc will render in. The rule holds for every schema version from v0 to v4 alike: `hueSpace` (#117, 2026-06-28) predates `schemaVersion` (#364, 2026-07-17), so a stored doc's version never implies its hue space, and only the field is read. The other table is never consulted (revision 5): the default hues are integers that differ between the forms (Primary `267` raw, `259` OKLCH), the hue slider steps by one, and a lookup that tried both stamped a pre-v5 OKLCH kit whose Primary the user had dragged to `267`, undoing the edit on load (U1 pass 1, M1), and the reverse case, and a fresh default kit whose `hueSpace` toggle had been flipped to `cam16` (its 16 OKLCH rows matched the OKLCH table, so the toggle's own render change was undone). Equality is `===` on the four numbers: `serialize`/`hydrate` keep an in-domain float byte for byte, so an unedited row matches exactly and a slider edit (integer steps) does not. `hydrateStoredDoc` calls it after the `hueSpace` stamp and before `hydrate`, so the stamp keeps its own contract (the function sees `"cam16"` on a legacy doc, and reads absence the same way if called on its own) and `hydrate`'s allowlist clamps the stamped hexes like any other (`clampHex`, uppercase). No `RENAME_MAPS` entry: the persist layer cannot see the default kit, and the stamp is about provenance, not a rename; the comment above `RENAME_MAPS` in `persist.js` is not edited (docs-repair's file), the new function's own comment says why it lives here.

## Risks

| Risk | What this plan does about it |
|---|---|
| a user-edited default row happens to equal a default row exactly, in its own hue form or the other one | in its own form it is then indistinguishable from unedited, and stamping the default anchor is the right render for it; a row edited by any slider step differs on an integer and is left alone (U1-4). The other form's value is a real slider position (Primary `267` in an OKLCH doc is eight degrees from its default `259`, and the reverse), so it must not match: the backfill reads only the table the doc's own hue space selects, and never the other one (U1-6; pass 1 tried both tables and stamped both directions, verdict M1). The one row whose two forms coincide (`Data 4`, hue `62`) renders the same either way, so a stamp there is harmless. A fresh default kit whose `hueSpace` toggle was flipped to `cam16` before v5 keeps its toggled render for the same reason: its OKLCH rows do not match the raw table (`1` stamped, `Data 4`) |
