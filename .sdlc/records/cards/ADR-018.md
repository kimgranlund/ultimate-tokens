# ADR-018 · `role-table.json` stays a hand-kept answer key; only the Figma-sandbox copy generates · 2026-07-17 · DECIDED (2026-07-17; TKT-0030/#342, informed by TKT-0019/#331)
| Field | Value |
|---|---|
| Decision | Partial: TKT-0019's build already collapsed three role-table copies to two (the binder's `roleTable(paletteName)` is `semanticRoles()`'s function body spliced verbatim plus its 3 `SCRIM_*` consts). The remaining pair `role-table.json` ↔ `semantic.js` is ruled WONTFIX for further generation; `role-table.json` stays hand-edited per `adding-semantic-roles` (no `gen:role-table` script) and the `refs-canonical` gate keeps deep-equaling `semanticRoles("primary")` against it. |
| Forces | the binder's copy existed for a purely technical reason (Figma's sandbox cannot `import` a `.mjs` at runtime) and carried zero independent verification value, `role-table.json` is a deliberately hand-authored independent answer key whose job is to catch an accidental behavioral change inside `semanticRoles()`, generating it from `semanticRoles()` makes the `refs-canonical` gate tautological, ADR-011 already ruled this file a golden master, the reverse direction is incoherent because the JSON carries rows for exactly one palette name while `semanticRoles(paletteName)` is name-parametric |
| Rejected | generating `role-table.json` from `semanticRoles()`; generating `semanticRoles()` from `role-table.json` |
| Consequences | `role-table.json` and `semantic.js` continue to move together by hand on every role/count change, an accepted ongoing maintenance cost. No test, script, or skill changes; the `refs-canonical` gate is unchanged. Revisit only if a genuinely new, unrelated reason to keep two independently generated copies surfaces. |
