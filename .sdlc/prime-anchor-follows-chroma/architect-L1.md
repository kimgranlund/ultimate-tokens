## Approach

The redesign collapses the three-layer chroma resolution (palette override, group default, dead global fallback) into two orthogonal layers, resolved in the one place that already exists for it, `src/engine/resolve.mjs`. Per palette: `chroma` (as today: key colour and prime strip only) and a new `baseChroma` (the ramp damper, 0..100, absent means 100). Global: `baseIntensity` and `primeChroma` keep their document field names (and the `stateOf` rename to `baseChroma` at the engine boundary) but change meaning to k factors multiplied onto every palette, default 100. `rampChromaOf(palette, controls) = (palette.baseChroma ?? 100) * controls.baseChroma / 100`, handed to `paletteStops` as the ramp palette's `chroma` exactly as the group value is today, so `dampStops` (`tonal.js:1518`, linear, `r >= 1` short-circuit) needs no change and composition order is moot. `primeChromaOf(palette, controls) = controls.primeChroma`. The `paletteGroups` chroma facet, `GROUP_DEFAULTS`, `locked` and `palette.primeChroma` are removed; `group` and `paletteGroup()` stay as the canvas grouping (rows, RP-1 export comment, DTCG `$extensions`, JSON `group`). Data palettes get the per-palette Base chroma like every other palette (REQ-002's "never overridable" retires with the groups).

The anchor rule from the first design carries over with `pc` renamed `k_prime`: on an anchored palette rung 3 holds the anchor's CAM16 hue and exact L* and scales the anchor's measured chroma by `k_prime`, gamut-capped, through the same `hctToRgb` the six rungs use; at `k_prime === 1` the stored bytes are returned verbatim (ADR-026's by-definition guarantee kept); the widening search's dedupe reseeds with the rendered rung-3 hex. `deriveKeyColor` (`src/ui/model.mjs:904`) applies the same factor with its own `hctToRgb`, never via `primeSwatches`, so the gallery tile and the prime middle agree at every k and the `key-anchor` gate keeps two independent producers. Identity at defaults now holds by construction: with the Material 60 gone, every default resolves to k 100 and every anchored middle is byte-exact at a fresh document. The per-palette Chroma slider keeps its detach semantics (`color.js:1765`, ADR-026) unless the user rules otherwise.

Migration is one `RENAME_MAPS` entry at schema v8 with four folds: (1) base chroma folds exactly (the resolved group value becomes `palette.baseChroma` when not 100; same number reaches `dampStops`); (2) prime values that resolved below 100 cannot fold byte-exactly and need the user's ruling (decision 1 below); (3) the two globals were unreachable before (`resolvePaletteGroups` at `model.mjs:455` fills every group, so `resolve.mjs:29` never fell through, verified: `doc.primeChroma 0` leaves every rung unchanged) and must be reset to 100 or a stale saved value would start damping everything; (4) `vibrancy 0` becomes 50 on pre-v8 docs, other values kept, `cuspPull` untouched. Curated presets carry no `schemaVersion` and an explicit `vibrancy: 0` stamped from `DEFAULT_CONTROLS` by `scripts/gen-categories.mjs:37`, so changing `tonal.js:70` restamps them on `npm test`; the three `?? 0` fallbacks (`tonal.js:1347, :1441, :1468`) must read `DEFAULT_CONTROLS.vibrancy` or partial-control gates (`anchor.mjs:80` carries no vibrancy) render at 0 while the app renders at 50. Measured consequences: default kit 256 of 304 display stops move, stop 500 stays the anchor 16 of 16, full-corpus perceptual AA floor 0 under with worst 4.503 (Adia data-3/light). Manifest: `/Users/kimgranlund/Projects/nonoun/ultimate-tokens/.sdlc/prime-anchor-follows-chroma/decompose/manifest-v2.json` (coverage clean, supersedes v1; report beside it).

Decisions that still need the user (recommendation first):
1. Migration of saved prime values below 100. Affected: 343 corpus Neutrals (Material default 60, unanchored, all seven rungs at 60 today), every saved kit's default Neutral (anchored, outer six at 60), Adia Primary (99). Options: C, accept the one-time move and record it in the before/after report (recommended: the vibrancy migration already moves every saved perceptual kit, and the strip becomes consistent); A, fold into `palette.chroma` (exact only in cam16 hue space since `effHue` at `tonal.js:102` reads the chroma fraction in oklch, moves the key tile, impossible for anchored palettes); B, keep `palette.primeChroma` as a hidden legacy field with no slider (byte-exact, but a rendering input with no UI).
2. Identity at defaults: with the group 60 gone, every anchored middle is byte-exact at defaults; what the migration changes is the Neutral strips above and all perceptual ramps via vibrancy 50. Confirm that is the intended reading of "saved kits do not move".
3. k composition: multiplicative product formed once in `resolve.mjs` (recommended, order-free because the damper is linear) versus k as a cap (`min`); and whether `k_prime` reaches the gallery key tile (recommended yes, tile equals prime middle).
4. Vibrancy 50: a saved explicit 0 is indistinguishable from the old default, so every pre-v8 doc at 0 becomes 50 (recommended); the chroma-envelope R69 bars at 50 are unverified and the plan re-measures them; the before/after report (`scripts/report-preset-fidelity.mjs --identity-control --base <main sha>`, the ADR-026 amendment precedent) is the ruling record.
5. The Chroma slider on an anchored palette: keep detach (recommended) or scale the anchor in place (needs a stored reference chroma).

T-0015 (hue space) does not constrain the chroma design beyond ordering: both tickets edit the anchored branches at `prime.mjs:147-153` and `model.mjs:905-908`; k is applied at the anchor's own hue in whichever space, in one helper, so T-0015 only swaps the hue source. Land T-0014 first.

## Rejected alternatives

- Keep a hidden per-palette prime factor to make saved kits byte-exact (option B): a rendering input with no control; recommended only if the user values exactness over the stated one-slider model.
- Group-relative identity (scale relative to the group default): moot once groups are gone; it would have made `prime.mjs` group-aware against REQ-008.
- k as a cap (`min(baseChroma, k)`): not what "applied to all colors" means and non-linear against the damper; the product is order-free.
- Apply `k_prime` to the prime strip but not the key tile: tile and middle would disagree at any k, the inconsistency the ticket started from, moved one surface over.
- Fix the ramp/prime defaults by changing `GROUP_DEFAULTS.material` instead of removing groups: the user removed the group layer; the fix would revert #785 R96 and keep the dead globals.
- Migrate vibrancy only when absent: presets and saved docs all carry explicit 0, so nothing would migrate; the user asked for saved kits to move to 50.
- Edit `tonal.js`'s envelope or damping to compensate for vibrancy 50: T-0013's territory; this ticket re-measures and re-rules, it does not retune.

## Risks

- Saved-kit movement is large by design: every perceptual kit's ramps (vibrancy), every default-kit-derived Neutral strip (60 to 100 outer rungs), the 343 corpus Neutral strips, Adia Primary. Without the user's ruling on decision 1 and the before/after report the plan cannot define "done".
- The AA floor margin at vibrancy 50 is 0.003 (Adia data-3/light 4.503): any later retune (T-0013) can red `corpus-contrast`; the gate's `EXPECTED_GALLERY` rows may need a re-ruled floor.
- Chroma-envelope R69 bars unverified at 50; a red there means a re-ruling in the ADR, not a tuning in this ticket.
- Resetting saved globals to 100 silently discards a value a user set; it never rendered, but the slider showed it. Record in the ADR and the DROPPED_KEYS report.
- ADR number is contingent on T-0013's landing order (last is ADR-028 at `decision-records.md:887`); `decision-records.md` and `tonal.js:70` are the shared serial slice.
- T-0015 touches the same anchored branches; landing order reversed would force a merge of two k/hue edits in `prime.mjs:147-153` and `model.mjs:905-908`.
- Schema v8 has no down-migration; a kit saved by the new app opens in an older build with `baseChroma` ignored and `paletteGroups` default-filled, so its ramps render undamped there.
- `test/ui/headless-boot.mjs` has 66 group mentions; the shim's DOM limits (building-editor-sections skill) bound what the new UI assertions can check.
