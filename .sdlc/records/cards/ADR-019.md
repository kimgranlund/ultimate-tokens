# ADR-019 · The theme axis is a data-driven `{name, side}[]` list, not a hardcoded Light/Dark pair; a role stays 2-ended · 2026-07-17 · DECIDED (ratified 2026-07-17; TKT-0021)
| Field | Value |
|---|---|
| Decision | Genericize the AXIS, not the per-role data model: a role keeps its 2-ended shape (a `light` ref and a `dark` ref); a theme is a named Figma mode bound to one of those ends via a `side` field. `semantic.js` exports `DEFAULT_THEMES = [{name:"Light", side:"light"}, {name:"Dark", side:"dark"}]`; `exportDTCG(state, opts)` takes optional `opts.themes` and emits one `"{name}_tokens.json"` per theme; `bindingTargets`/`bindingPlan` take the same list (per-role shape changed to a generic `targets: [{mode, target}, ...]` array); `applyBundle` walks every theme file the bundle carries (identified by `$extensions["com.figma.modeName"]`) and creates exactly that many Color Roles modes, pruning unwanted ones. Absent `opts.themes` reproduces the pre-ADR-019 output byte-identically, proven by an explicit before/after diff. |
| Forces | the 2026-07-17 collections-architecture review (CRITICAL-3) found the breakpoint axis fully generic while the theme axis was hardcoded to exactly two in `exportDTCG`, `bind-plan.mjs` and `applyBundle`, adding a third theme required an engine change not a config change (TKT-0021), a third resolved end per role would require a new field in the role table with role-count-style lockstep concerns, a theme can already reuse either existing end under a new name |
| Rejected | a third resolved end per role (a "Dim" carrying its own color distinct from Light and Dark), deferred as separate future work |
| Consequences | `figma/binder/figma-semantic-binder/code.js` still hardcodes its own Light+Dark mode creation (out of scope for TKT-0021); the two binders stay compatible because a 3-theme axis reusing an existing `side` contributes no new raw names (`test/figma/binder.mjs` `themes` gate), but the standalone binder does not yet let a user create a 3rd Color Roles mode. `exportUI3`'s `Color Roles` collection was NOT touched and carries the same hardcoded-pair pattern (a documented gap). No UI control was added for authoring extra themes; wiring one is a separate later decision. Follow-up: genericize `exportUI3` and the standalone binder the same way if a real 3rd-theme ask lands (tracked informally, not a filed ticket). |
