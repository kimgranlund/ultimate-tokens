# ADR-002 · Semantic export ships RESOLVED colors, not aliasData · 2026-07-12 · DECIDED (default kept)
| Field | Value |
|---|---|
| Decision | Light/Dark semantic DTCG files contain resolved colors with no `aliasData` by default. A `rawColl` field opts into emitting `aliasData`. |
| Forces | Figma "Modes for variables" docs, cross-collection `aliasData` needs library-key UUIDs Figma only mints on export, name-only aliasData errors on native import ("errors importing N tokens") rather than falling back, resolved colors always import |
| Rejected | Semantic tokens that alias raw cross-collection so edits cascade on import (the ideal) |
| Consequences | No cascade via JSON import; cascade is delegated to the plugin (the binder). Resolved files are larger but reliable. Re-verified 2026-06-15: the `com.figma.aliasData` extension documents a fallback hierarchy (`targetVariableID` → `targetVariableName` within `targetVariableSetID` → `targetVariableName` within `targetVariableSetName`), so name + collection-name aliasing IS a documented path when the target collection already exists in the file; the original framing is softened but the decision stands, resolved stays the always-safe default, pure name-only behavior remains undocumented. Feeds OD-004. Spike 2026-06-17: `rawColl` already emitted `targetVariableName` + `targetVariableSetName`; the export verifier now asserts both on every aliased semantic leaf (`hpg-export-resolved` / AC-X6). SHAPE conformance only; the native-import cascade is still unvalidated end-to-end (no Figma in CI) and unexposed in the UI. Advances OD-004 to a gated spike, not a decision. |
