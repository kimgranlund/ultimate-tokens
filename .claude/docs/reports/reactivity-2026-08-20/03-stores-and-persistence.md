## (B) Inconsistencies

1. **HIGH** — `isDirty()` (`app.js:194-196`) is compared against a **raw, non-key-sorted** `JSON.stringify`, while the test harness's own equality (`test/ui/persist.mjs:11-12`, `deepEq`/`srt`) deliberately **sorts keys before comparing**, because persist.js's own header claims "byte-for-byte" but several commit paths build sub-objects by **spreading the existing object then appending a new key** (e.g. `settings.js:84` `_setExportUnit`: `{...(d.export||{}), unit}`, `settings.js:123-129` `_setNamingScheme`) rather than reconstructing in `clampExport`'s canonical field order (`persist.js:409`: `unit, colorPrefix, typePrefix, geomPrefix`). Two docs with **identical field values but different edit history** can carry `export`/`voices`/etc. sub-objects with different live key order. No live bug found today only because `save()` always re-serializes the *same* live `this.doc` object immediately after every mutation (`edit()` at `app.js:221-227` unconditionally calls `save()`), so `savedSnapshot` and the next `isDirty()` check are reading the same object graph — but this is a fragile coincidence of the current call graph, not an enforced invariant. A future path that rebuilds `this.doc` (or a sub-object) without an immediately-following `save()` would produce false dirty/clean readings.

2. **MEDIUM** — `isDirty()`'s "dirty" branch is **currently unreachable** [synthesis correction: reachable via `selectPalette()` — see report 01 §B1; the cost half of this finding stands]. Every reassignment of `this.doc` (`openSet` at `app.js:178`, `_restore` at `app.js:367`) is a wholesale replacement immediately followed by `save()`/`this.savedSnapshot=...` in the same call, and every other mutation goes through `edit()` (`app.js:221-227`), which unconditionally calls `save()` right after `fn(this.doc)` — including live drag edits (`opts.live`). There is no code path today that mutates `this.doc` and defers `save()`. The "unsaved" state of the `.af-save` footer badge (`app.js:2164-2169`) is therefore dead UI, and `isDirty()` pays a full `serialize()+JSON.stringify()` cost on every `paintAppFooter()` call (every render **and** every `liveRefresh()` tick) to always report "saved."

3. **MEDIUM** — Migration-chain gap. `migrateStorageKeys()` (`app-helpers.mjs:74-84`) only walks the two historical product-rename prefixes for **`-sets`/`-project`/`-profile`** suffixes. **App prefs and apply-consent are excluded entirely** — their keys are hardcoded to the *current* product name literal (`"ultimate-tokens-app-prefs-v1"`, `"ultimate-tokens-apply-consent-v1"`) rather than derived from `STORAGE_KEY` the way `SETS_KEY`/`PROJECT_KEY`/`PROFILE_KEY` are (`app-helpers.mjs:17-23`: `STORAGE_KEY + "-sets"` etc.). This is a **deliberate, commented** choice ("versioned like the apply consent" / "a fresh profile... boots identically to pre-prefs builds," `app.js:2247-2250`) since both are safe-to-reset cosmetic/safety state — but it means the sets/project/profile trio gets forward migration across a rename while prefs/consent do not, a real asymmetry in the store's own discipline that a reader of `migrateStorageKeys()` alone wouldn't discover (it isn't mentioned there).

4. **MEDIUM** — Two-tier clamp rigor. Only the **doc store** (persist.js `serialize`/`hydrate`) has the sealed, fuzz-tested roundtrip-identity + per-field-clamp gate, `schemaVersion` + `RENAME_MAPS` translate-forward machinery, and a dedicated allowlist-parity test (`test/ui/persist.mjs`, all ~340 lines). The **profile** store's `clampProfile()` (`src/engine/flags.js:82-108`) is a real, well-typed allowlist clamp with idempotence spot-checks (`test/engine/flags.mjs:50-91,161-170`) but **no fuzzed roundtrip/per-field gate and no rename-map mechanism** — a `FLAG_KEYS` rename has no recovery path at all (worse than persist.js's `voices`, which at least gets `RENAME_MAPS` on a documented rename). The **sets index** and **PROJECT_KEY** slot have **no validation of their own shape** whatsoever — ad hoc `JSON.parse`+try/catch only, entirely dependent on each doc being independently hydrated later. **App prefs** validation is hand-inlined per call site rather than routed through any shared clamp helper.

5. **LOW** — `clampTokenOverrides` (`persist.js:425-436`) validates key **arity** (3 segments for type, 2 for geom) and the numeric range, but — as the file's own comment documents at `persist.js:227-231` — **never checks the leading voice/size segment against `VOICES`/engine domains at all**, unlike `clampType`'s `voices` map (`persist.js:483-484`, `t.voices[name]` gated by `VOICES.includes`). This is a *different* failure mode from the documented "silent drop" landmine: a `voices` override for an unknown name is dropped (potential data loss, now partly mitigated by `RENAME_MAPS`); a `tokenOverrides` key for an unknown/typo'd/retired voice or step is **never dropped and never applied** — it survives every hydrate as a permanently inert, silently-accumulating orphan (dead storage weight, and a latent hazard if a voice/step name is ever reused for something else in the engine).

## (C) Drift / data-loss risk scenarios

- **Gallery crash on a malformed set record.** `buildTiles()` (`app.js:628-630`) does `this.sets.filter((s) => !q || s.name.toLowerCase().includes(q))` with **zero guard** on `s.name`. `loadSets()`/`receiveStoredSets()` never validate individual record shape (see (A) row 1 and (B)#4) — a set record that's missing `.name` (a future bug, a hand-edited `localStorage["ultimate-tokens-sets"]`, or a lossy Figma `clientStorage` write) throws a `TypeError` on `.toLowerCase()` and takes down the **entire gallery render**, not just that one card, on every keystroke of the search box.
- **Voice rename without a `RENAME_MAPS` entry.** The file is explicit (`persist.js:200-219,447-450`) that this is a live, previously-hit failure class (the 2026-07-13 voice taxonomy rename originally hit exactly this before `RENAME_MAPS` existed). The `allowlist-parity` test (`test/ui/persist.mjs:305-329`) only checks that `persist.js`'s hand-copied `VOICES`/`TYPE_TREATMENTS`/`GEOMETRY_TREATMENTS` **sets** match the engine's — it does **not** know whether a *rename* (vs. an add/remove) needs a `RENAME_MAPS` entry; that's a human judgment call each time, gated only by `npm test` being run before merge. A hotfix or an out-of-band edit that adds a rename map entry to `type.mjs`/`geometry.mjs` without a matching `persist.js` `RENAME_MAPS` bump ships silently — every user's per-voice override for the old name vanishes on their very next save/reload, with no error, no toast, nothing (`t.voices[name]` for the old name is simply absent from the filtered allowlist).
- **Rename-again event (a third product rename).** Given the repo has already renamed twice (the two pre-rename storage prefixes `migrateStorageKeys()` walks — see `app-helpers.mjs:74-84`), a third rename would correctly carry forward sets/project/profile via `migrateStorageKeys()`, but app-prefs and the apply-consent flag would **silently reset** (theme/motion/font-mode revert to defaults; the "back up your variables first" warning re-shows once). Low-severity by design, but worth flagging since it's an emergent property of (B)#3 rather than a deliberate, documented decision made *at* migration time.
- **Slider-drag persistence storm** (see the cost story below) — not data loss, but a real risk of dropped/late Figma `clientStorage` writes or a laggy/'buggy' drag under load, which the code's own comments already flag as an observed symptom (`app.js:243-245`) but attribute only to the DOM-render cost, not to the unthrottled storage write identified here.

## Cost story — the finding worth flagging up

`editDrag()` → `edit(fn, {live:true})` (`app.js:221-227,321-326`) unconditionally calls `save()` **on every single native `input` event**, not just once per drag. The pointer-drag driver (`_bindRangeDrag`, `app.js:2087-2124`) dispatches a fresh `input` event on **every `pointermove` tick** (unthrottled — no rAF gate; contrast this with `liveRefresh()`, which *is* explicitly coalesced to one DOM rebuild per animation frame via `requestAnimationFrame`, `app.js:246-251`). So per pointer-move tick during a slider drag:

1. `serialize(this.doc)` — a full `JSON.stringify`+`JSON.parse` deep clone of the **entire active document** (all palettes, type voices/overrides, geometry modes, role overrides…).
2. A second full `JSON.stringify` of that same object for `savedSnapshot`.
3. `persistSets()` → `saveSets(this.sets)` → `JSON.stringify({sets: this.sets})` — stringifying **every other set in the gallery too**, not just the one being edited, followed by a synchronous `localStorage.setItem`.
4. **In Figma only**: a `postMessage` of the **entire `this.sets` array** across the iframe/sandbox boundary (structured-clone cost) — also on every tick, also unbounded by gallery size.

This is unbounded by drag duration and scales with total gallery size (docs × complexity), not just the edited doc. It is a strong candidate root cause — alongside the DOM-render cost the code already blames — for the "buggy when dragging" behavior in Figma's iframe that the comments at `app.js:2081-2086` describe. The 250ms debounce in `editDrag`/`commitDrag` (`app.js:321-338`) only coalesces the **undo-history push**, not the storage write.

## (D) Verdict

**Several accreted disciplines, not one architecture.** The **doc store** (persist.js) is the one part of this system built to an actual spec: a pure `serialize`/`hydrate` pair with a sealed fuzz-tested roundtrip+per-field-clamp invariant, a `schemaVersion`+`RENAME_MAPS` forward-migration mechanism, and a parity test keeping its hand-tracked allowlists honest against the engine. Everything else — the sets index, the profile, app-prefs, the PROJECT_KEY slot, and both Figma channels — is a **second, much looser tier**: ad hoc `JSON.parse`/try-catch at the storage boundary, with clamping deferred (correctly, but only informally) to the moment each doc is actually opened, and with `clampProfile` as an honest but less-tested allowlist clamp that has no rename-forward story at all. The `-v1`-suffix keys (app-prefs, apply-consent) are a third, even lighter pattern — "version" means "cache-buster," not "migratable," and by design sit outside `migrateStorageKeys()` entirely. None of these tiers is wrong in isolation (the lazy-clamp-at-open pattern is a reasonable, consistently-applied design, and the safe-default-on-reset choice for prefs/consent is defensible), but they weren't designed together: a reader who internalizes persist.js's rigor and assumes it extends to `clampProfile`, the sets array, or the app-prefs key would be wrong on all three counts, and the one place that pattern-matches "obviously exercised a lot" — the slider-drag edit path — turns out to run a full-gallery persistence write on every pointer-move tick, unthrottled, which nothing in the current test suite (headless-shim, no perf assertions) would ever catch.
