# ADR-011 · OKLCH-native hue model + chroma-aware OKLCH→CAM16 inverse · 2026-07-12 · DECIDED
| Field | Value |
|---|---|
| Decision | The doc-level `hueSpace` default flips cam16 → oklch, so the per-palette `hue` is an OKLCH hue by default (cam16 stays selectable; legacy cam16 docs carry `hueSpace:"cam16"` explicitly and keep rendering in cam16). `oklchToCam16Hue(h, chromaFrac=1)` becomes a Newton inverse of the render path anchored at the palette's own chroma, and a new high-res `hctToOklch` converts straight through OKLab with no 8-bit round-trip; `projectView` emits `keyOklch` and the key HEX is derived from it. |
| Forces | ADR-008's fixed mid-sample OKLCH→CAM16 mapping drifted a few degrees (worst ~15° at the blue/violet pole), the user is fluent in OKLCH and entered hues landed off, the OKLCH↔CAM16 hue map shifts with chroma (Abney effect) so a fixed or cusp-only anchor is wrong at the other end, principle that HEX is only derived for consumption and perceptual coords come from the model at full precision |
| Rejected | none named |
| Consequences | Producers emit OKLCH hues: `gen-categories` stores each preset's source OKLCH hue and bakes `hueSpace:"oklch"`; `seedFromKeyColor(oklch, hueSpace="oklch")` returns the input's OKLCH hue (or CAM16 for a legacy cam16 doc); `defaultDocument` converts the 8 starter CAM16 hues to OKLCH via `camHueToOklch`. `role-table.json` is UNCHANGED (still the cam16 answer key; parity gate intact). `hctToRgb` is byte-identical (refactored to share `_hctToLinRGB`). Engine gate `hct-oklch-inverse` in `test/engine/hct.mjs`. Rendered identity color lands on the stored OKLCH hue to ~0.00°. |
| Supersedes / amended by | Supersedes ADR-008; complemented by ADR-012; cited as precedent by ADR-018 |
